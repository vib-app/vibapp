# VibApp 可行性评估

状态：评估完成（2026-08-11），结论为 **有条件 GO**。先通过版本化合同与安全门禁，再进行未发布的本地 Stage 0 实现；公开 Registry、云端生成和产品发布需后续独立验收与授权。

## 执行结论

VibApp 的核心产品闭环是可实现且合理的：用户用自然语言描述需求，系统先检索 Registry 并解释匹配原因；用户可以安装合适模块，也可以在明确的隐私与发布同意后，让本地或云端 Code Agent 生成定制模块。

项目可以进入开发，但必须接受四项架构修正：

1. 社区模块不能作为原生 Rust 动态库直接注入客户端进程；模块应编译为受限的 WebAssembly Component，并通过版本化 WIT 接口调用主机能力。
2. “兼容任何版本客户端”应改成“兼容同一稳定 Host API 主版本，并通过能力协商与兼容性测试验证”。绝对跨任意版本不可验证，也无法长期保证。
3. 闹钟、通知、后台运行等系统能力由可信主机实现；模块只声明计划和权限，避免模块崩溃导致闹钟失效。
4. 云端生成和公开分享是两个独立动作。云端执行前要确认远程处理；公开前还要展示将公开的需求、源码、许可证和扫描结果并再次确认。

## 需求逐项判断

| 需求 | 判断 | 首版实现边界 |
| --- | --- | --- |
| 桌面 Launcher / GUI | 可行 | 它是所有已安装 VibApp 的启动器与宿主 Shell，同时承载 AppStore、AI 搜索和开发入口；Rust UI + 系统 WebView，按平台验收 |
| Linux / 树莓派 CLI | 可行 | 复用同一 daemon/control protocol；管理 UI、服务和混合包，完整运行 `headless` 服务，UI 包在无图形环境只可管理不可渲染；优先级低于桌面与 Web 预览 |
| vibapp.ai 网站 | 可行 | Registry、搜索、详情页、聊天与构建状态；系统级功能仍由本地主机或云运行时执行 |
| 本地服务 | 可行 | 独立 Rust daemon，负责安装、权限、调度、状态和模块生命周期 |
| Registry 语义检索 | 可行 | 结构化硬过滤 + 关键词/向量混合召回 + 重排；匹配说明只能引用真实元数据 |
| Rust 模块热加载 | 有条件可行 | WebAssembly Component、内容摘要、签名、权限清单、原子切换和回滚 |
| 任意客户端版本兼容 | 原要求不成立 | 改用 Host API 版本范围、能力协商、迁移函数和兼容测试矩阵 |
| 本地 Codex 开发 | 可行 | Codex Agent 与编译容器分离；本地生成默认私有，发布必须主动选择 |
| 免费云端开发并自动分享 | 技术可行、产品上需收紧 | 限额/排队；远程处理与公开发布双重同意；秘密扫描与许可证确认 |
| 全部代码使用 Rust | 大部分可行 | 业务、服务、客户端、Web UI 和模块逻辑用 Rust；WIT、TOML、CSS、SQL、容器配置属于必要声明文件 |

## 建议的系统边界

```text
Desktop Launcher / Web UI
        |
        v
Conversation Orchestrator ---- Registry Search / Metadata / Trust
        |                                  |
        | no acceptable match              | signed component
        v                                  v
Local or Cloud Agent Runner ------> Build / Test / Scan / Sign
                                               |
                                               v
                                  Local Daemon / Cloud Runtime
                                               |
                                  Versioned Host Capability API
                                               |
                                      Wasm App Component
```

### 可信主机

主机负责身份、权限提示、密钥隔离、持久化、计划任务、通知、网络白名单、资源配额、日志和升级回滚。模块永远不能直接取得宿主文件系统、Docker socket、用户凭据或任意网络访问。

### Launcher

桌面 GUI 的主身份是 VibApp Launcher 与统一应用管理器，而不是单独的商店客户端。它展示和启动所有本地 App，维护最近应用与运行/更新状态，并负责安装、卸载、启用、禁用、设置、权限、状态、日志和升级入口。AppStore、对话搜索、安装和开发任务是 Launcher 内的系统页面。模块打开后由 Launcher 渲染其声明式视图并转发语义事件；模块不能替换 Launcher 的可信标题栏、权限提示或系统导航，也不能读取其他 App 的界面、会话或状态。真正的实例、后台任务、权限和热更新仍由本地 daemon 持有。

VibApp 包可声明三种形态：仅 UI、无界面后台服务、UI + 服务混合。后台服务仍采用宿主调度的事件驱动模型。例如温度上报服务通过明确的系统指标、计划任务和限定目标网络权限工作，不能直接读取任意硬件或联网。禁用会停止服务、调度和副作用但保留包与数据；卸载必须明确选择数据保留、导出或删除，关闭 UI surface 不等于禁用混合应用。

跨平台兼容由 Manifest profile 表达：`desktop`、`web-preview`、`web-runtime` 和 `headless`。vibapp.ai 可在隔离 Worker/预览区加载可信构建链派生的 Web 产物并渲染同一声明式 UI；本机硬件、长期后台任务和桌面权限在预览中使用明确标注的模拟/不可用能力，不能伪装成真实运行。

### VibApp 模块

模块是事件驱动的 Rust 组件，输出声明式 UI/动作，不向宿主注入原生窗口代码。建议的最小生命周期是：

- `manifest()`：返回身份、版本、Host API 范围、能力和权限。
- `init()`：初始化模块状态。
- `handle(event)`：处理用户、定时器和主机事件。
- `render()`：返回宿主可渲染的声明式视图。
- `checkpoint()` / `restore()`：支持升级、回滚和跨设备迁移。

### 安装与热更新

安装流程必须按“下载 → 摘要校验 → 签名/来源验证 → 权限确认 → 预实例化 → 兼容性检查 → 原子切换 → 健康检查”执行。失败时保留旧版本和状态快照。

## Registry 检索

不能只做向量相似度。推荐流程：

1. 从完整对话提取显式需求、平台、时间语义、离线要求、权限上限和否定条件。
2. 先按 Host API、平台、能力、权限、发布状态和可信等级做硬过滤。
3. 使用全文与向量混合召回。
4. 对候选进行需求覆盖率、权限成本、可信度和维护状态重排。
5. 返回逐条需求覆盖证据、缺口、所需权限、来源和构建摘要。

Registry 元数据至少包含：不可变 ID、语义版本、内容摘要、Host API 范围、能力、权限、支持目标、作者、许可证、来源、生成方式、源码位置、签名、SBOM、扫描结果、发布时间和撤销状态。

## Code Agent 与编译器

Agent Runner 和 Compiler 应是两个安全边界：

- Agent 只在一次性工作区内生成或修复源码。
- 编译器使用固定 Rust 工具链、锁定依赖和无特权容器构建。
- 构建默认无网络；依赖通过受控缓存或显式取回阶段进入。
- 不挂载 Docker socket、用户主目录、SSH 目录或长期 API 密钥。
- 每次产出运行格式化、静态检查、单元/集成测试、Host API 兼容测试、依赖审计、SBOM、恶意行为扫描和摘要签名。

本地开发默认私有。云端开发需要先解释上传内容、执行位置、保留期限和费用/额度，再取得远程处理同意。公开分享需要单独展示最终公开内容与许可证。

## 闹钟纵向样例

闹钟模块用于验证整个架构，而不是只验证 UI：

- 用户提出工作日、时区、重复规则、铃声、贪睡和离线要求。
- Registry 能解释已有模块覆盖与缺口。
- 安装时展示“计划任务、通知、音频”权限。
- 模块把计划提交给主机；主机持久化并调用各平台通知/后台 API。
- 模块升级后，旧计划和用户状态可以迁移；升级失败自动回滚。
- 桌面断网或模块未运行时，已提交给主机的闹钟仍能触发。

## 分阶段路线

### M0：架构验证

- Rust workspace、协议类型和 WIT Host API。
- 内存 Registry 与可解释的混合检索接口。
- 本地 daemon、模块安装状态机和模拟运行时。
- Codex adapter、固定输出 schema 和 Docker 编译器。
- 示例闹钟模块及端到端测试。

### M1：本地可用产品

- 桌面 GUI、聊天、搜索结果卡、权限确认、本地安装与热更新。
- Launcher 应用启动台与安装/卸载/启用/禁用/设置/状态/日志管理；支持 UI、服务和混合包。
- 真实 Wasm 运行时、持久化、系统通知/计划任务适配。
- 本地生成、构建日志、失败修复循环和选择性分享。

### M2：Registry 与网站

- vibapp.ai Registry API、PostgreSQL/pgvector、对象存储和签名发布。
- 网站搜索、详情、构建状态、账号、举报与撤销。
- 对 `web-preview` 兼容包提供隔离 Wasm Worker 预览，清楚标注模拟能力与浏览器限制。
- 从网页通过深链唤起本地客户端并二次确认安装。

### M3：云端生成

- 隔离构建 worker、队列、额度、内容与秘密扫描。
- 远程处理/公开发布双重同意、许可证和来源证明。
- 多 Agent adapter；Codex 先行，随后再增加 Claude Code、OpenCode。
- 增加面向 Raspberry Pi、Ubuntu Server 等命令行环境的 `vibapp` CLI，提供人类可读与稳定 JSON 输出。

## Go / No-Go 门槛

首版可以开工，但以下门槛在进入公开测试前必须满足：

- 未授权的模块无法访问文件、网络、通知、计划任务或凭据。
- 一个针对旧 Host API 构建的样例可以在兼容主机上安装、升级、迁移状态并回滚。
- Registry 的匹配解释可以追溯到元数据，且硬性否定条件不会被相似度覆盖。
- 构建容器无法访问宿主 Docker socket、主目录或长期密钥。
- 云端处理和公开分享都有独立、可审计的同意记录。
- 闹钟在模块退出和网络断开后仍由主机可靠触发。

## 尚待外部确认

- `vibapp.ai` 已注册并配置 Cloudflare nameserver，但本环境访问 HTTPS 超时；域名控制权和部署入口尚未验证。
- “永久免费”的长期经济模型尚无成本数据支撑，首版应使用测试额度、队列和单用户配额，不承诺无限免费。
- “App Store/AppStore”可能涉及商标和平台政策，公开品牌文案上线前需要法律/商标审查。
